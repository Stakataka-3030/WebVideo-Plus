# Disposable Windows CI host startup gate

This gate runs only after the complete Craft package and embedded installer payload have been built and statically verified. It is not a test for a user's desktop. Both preparation and execution refuse anything except an explicitly enabled GitHub-hosted Windows Actions runner. Local verification is limited to syntax, static fixture checks, pure guards, and one hidden console-process identity check in `ci-host-smoke.test.mjs`. That check starts only its own PowerShell process, not a GUI or Craft.

`ci-host-inputs.lock.json` pins the public official Craft 1.0.0 installer archive, its extracted unchanged host EXE, and the 7-Zip extraction tool. `prepare-ci-host.ps1` uses the existing `Get-PinnedBuildInput` SHA-256 mechanism, verifies lengths and extracted hashes, and extracts only the host EXE. Neither the official NSIS installer nor the 7-Zip installer is executed. There are no downloaded media inputs in this minimal test.

The independently named CI step performs these real operations:

1. Install the complete current package through its shipped transaction CLI into a fresh runner temporary directory.
2. Start the original-name entry with an independent WebView profile. Verify its session belongs to that wrapper PID and exact official host path.
3. Require both launcher `ready` and the actual session `injected` record with `verified-loopback-owned`. Verify the real native listener again before connecting CDP.
4. Read the official `tauri.localhost` page and confirm that the actual enhanced bootstrap, bridge, and mounted DOM exist. On the empty first-run welcome page the tools dock may be parked/hidden; this is not a claim of editor toolbar visibility or interaction.
5. Send normal close only to the exact owned host process, using a retained process handle after checking executable path and creation time. Require successful wrapper exit, `closedAt`, released session lock, and eventual exit of the captured process descendants.
6. Unmount through the shipped CLI and verify the exact official EXE and immutable input package hashes are restored/preserved.

This minimal gate explicitly reports editing, preview, and short export as `NOT_RUN`. Existing native graphics/export gates remain separate. It does not prove official NSIS updating, user account integration, AI providers, private SDKs, or performance on a particular user's GPU. A pass must come from the final CI commit; local syntax/unit tests cannot substitute for a host result.

## Independent gates and unaccepted candidates

The complete installer/static payload build is followed by the independent production, native graphics/export, and scene-only tail gates. Only after those succeed does the unchanged real-host gate run. Host failure still fails the job; neither failure nor `NA` becomes a pass. The existing `webvideo-craft-windows-test-installer` artifact keeps its original name and default success condition after the host gate, so it is not uploaded when any gate fails.

Before starting the host, CI may preserve a separately named `webvideo-craft-host-unaccepted-candidate` for isolated CLI acceptance. Its EXE is the exact complete-build installer, accompanied by `candidate.json` with `HOST_UNACCEPTED`, `releaseAccepted: false`, `NOT_RUN_AT_CAPTURE`, source commit/run ID, version, bytes, installer SHA-256 and manifest/kernel hashes. The record requires the successful full installer/payload identity check from the same source and rehashes the current EXE; it contains no formal release declaration. The candidate remains unaccepted even if a later check succeeds and must never be promoted or published merely because the artifact exists. This preserves useful independent evidence without weakening the release gate or repeating token-reduction experiments.

The official host's native Known Folder settings and single-instance mutex are not isolated merely by changing APPDATA/LOCALAPPDATA or using a second Win32 desktop. That is why the unchanged host is restricted to the disposable remote runner. No personal files, credentials, projects, profiles, SDKs, or native global logs are copied to CI or uploaded. The smoke artifact is an allowlisted JSON result containing only this run's assertions and sanitized startup errors. Temporary test trees stay runner-local until the runner is disposed.

Failure cleanup is restricted to descendants of the exact spawned wrapper or already verified surviving children. Every process is rechecked by executable and creation time through an opened process handle. CIM and native start timestamps are compared at their exact common microsecond precision, not within a time window. No name-wide termination, foreground desktop switch, host patch, single-instance bypass, security-check skip, or silent success on an unavailable graphical environment is permitted.

## Failure evidence

The CI observer samples at most 18 target summaries while the unmodified production launcher performs its own wait. Before every diagnostic endpoint read it independently verifies the native loopback listener and its host ancestry. A failed ownership check prevents that read. Each retained target contains only type, URL origin and path, never title, ID, query, fragment, WebSocket URL or tokens. Counts distinguish no candidates, multiple candidates and other origins without accepting any of them as a production target. Runtime version, bounded lifecycle stages, owned process state and remaining owned processes are also recorded. No fixed startup delay, relaxed origin, or extra production retry is introduced.

The official native log is read only from bytes appended during this CI run. Only classified initialization/error/panic events, error codes and line digests are retained, never raw lines. Native stdout/stderr is still ignored by the production launcher, so this is not complete panic coverage. Cleanup subprocess failures contain code, signal, killed, an explicit abort-timeout result, elapsed time and short stderr. Progress-only PowerShell CLIXML and full EncodedCommand arguments are not retained.

## Independent port diagnostic, not release acceptance

`craft-host-port-diagnostic.yml` runs on pushes to `diag/craft-debug-*`, or explicit workflow dispatch. It needs no product/npm/native-exporter build. An integrator can push the reviewed diagnostic commit to `diag/craft-debug-token-20261109`; that name is intentionally outside the full native-smoke workflow's push branch list. The result is the `craft-host-port-diagnostic` artifact, not a release installer or host-gate pass.

Preparation uses the same fixed official host/extractor lock and SHA/length checks. It statically extracts the unchanged host, compiles the current production native listener verifier and a separate query-only token helper. It never runs the upstream installer. The hosted-only probe serially starts two fresh copies under the production original-EXE basename, with the production loopback debug arguments and independent WebView profiles. `fixture-env` adds the current smoke's four APPDATA/LOCALAPPDATA/TEMP/TMP overrides; `profile-only` leaves those inherited. Direct host launch intentionally omits product installation, wrapper coordination and payload injection, so these are **not tested** by this diagnostic.

The report contains exact owned-process token elevation type, integrity RID/class and linked-token availability, plus booleans for whether the actual WebView command line contains the expected debug port/address/profile. It retains no raw command line, environment or profile path. The query helper rechecks executable/start time through the same opened process handle, requests TOKEN_QUERY only and never creates, filters or changes tokens. Before a target HTTP read the unchanged native verifier must confirm loopback ownership; only target type/origin/path summaries are retained. Captured native stdout/stderr is capped at 64 KiB and reduced to event classes, codes, digests and debug-disallowed/listening booleans.

Only these registry observations are allowed: HKLM/HKCU `SOFTWARE\Policies\Microsoft\Edge` values `RemoteDebuggingAllowed` and `DeveloperToolsAvailability` (presence and bounded numeric value), and exact values `*`, `webgal-craft.exe`, `webgal-craft.webvideo-original.exe` under its `WebView2\AdditionalBrowserArguments` key (presence/debug-port-presence only). `GetValue` reads literal names without enumerating other values. No registry/configuration writes, account creation, token lowering, ACL changes or security-policy bypass are included. Cleanup requests normal close of the exact host, then may terminate only previously verified owned identities. Any remaining owned process blocks the next variant.

The leading hypothesis for CI run 42643700577 is WebView2 150+ ignoring debugging environment overrides in an elevated/high-integrity host. Runtime 156 was reported, while the host and WebView remained alive without a listener. This remains a hypothesis until the run's token/actual-switch evidence is available. Microsoft describes the restriction as an intentional local privilege-escalation fix ([maintainer explanation](https://github.com/MicrosoftEdge/WebView2Feedback/issues/5640#issuecomment-4923662109)); [wry #1782](https://github.com/tauri-apps/wry/issues/1782) reports the matching hosted-Windows symptom. [GitHub documents administrator/UAC-disabled Windows VMs](https://docs.github.com/en/actions/reference/runners/github-hosted-runners#administrative-privileges). We do not move environment flags into API/HKLM configuration or change those protections to make a test pass.
